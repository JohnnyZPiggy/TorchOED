# TorchOED vision (Scientist direction, 2026-11-01; v4 2026-11-17 — the Scientist edits this file, the loop does not)

## North star
**One PyTorch-native engine for the whole of optimal experimental design** — classical exact designs, industrial DOE, nonlinear and Bayesian model-based designs — that matches or beats PyDOE, R (AlgDesign, OptimalDesign, skpr, acebayes, ICAOD, FrF2/DoE.base, rsm) and JMP's Custom Designer on quality, adds what none of them combine, and scales on GPU.

Today these capabilities are spread over a dozen tools with different languages, criteria definitions and no quality guarantees. TorchOED unifies them under one tensor contract.

## Four signatures (what makes it more than "another DOE package")
1. **Certified designs everywhere.** Every returned design carries a proved lower bound on its efficiency (Kiefer–Wolfowitz/equivalence-theorem duality for D, A, I and compound criteria), not just a number.
2. **Autograd-native model-based design.** Users write a model `f(x, θ)` in torch; Fisher information comes from Jacobians, so nonlinear local, Bayesian (prior-averaged) and robust/minimax designs need no hand-derived formulas.
3. **GPU scale.** Batched low-rank exchange over 10⁵–10⁶ candidates, many restarts and Monte-Carlo prior draws in parallel, with end-to-end measured (never assumed) speed.
4. **Differentiable and composable.** Continuous factors optimized by gradients, designs as tensors that plug into BoTorch/Ax/active-learning loops.

## Guardrails
- **Completeness rule (Scientist decision 2026-11-16: "全面点，仔细点").** A capability is *complete* only when its matrix row has every cell filled with evidence or an explicit, reasoned N/A: (1) criteria D, A and I; (2) composes with `fixed_ids` augmentation and with candidate constraints/categorical coding, or raises a documented error; (3) a proved efficiency lower bound, or an explicit `LOCAL_ONLY` certificate with the reason and a Mentor Issue — never silent; (4) `design_diagnostics` (correlation, VIF, SPV/FDS, power) correct for that structure; (5) CPU float64, plus a measured GPU result where the work is search-heavy; (6) an exact small oracle (Fraction or exhaustive enumeration) and one external published reference where one exists (else NOT_RUN recorded); (7) API entry, a runnable guide snippet and a CHANGELOG line; (8) at least one held-out case. Every feature PR updates its matrix row. Week goals are chosen from the open rows of the current phase first; at most 3 feature goals per week, so each is finished properly rather than started.
- **Parity plus advantage (Scientist decision 2026-11-16: "媲美 R 包和 JMP，同时有自己的优势").** Parity is measured row by row against the parity checklist (JMP 18 DOE platform and the R packages named in the North star), never by impression. Every phase exit must also demonstrate at least one of the four signatures on a published example: a certificate the reference tool cannot give, a measured GPU speed-up at equal quality, an autograd/neural-network model no reference tool accepts, or a differentiable continuous design without a candidate grid.
- **Library first, light Studio (Scientist decision 2026-11-17, replacing "Library, not GUI").** The core library stays GUI-free and is never slowed by the Studio. The Studio is a thin, separate client of the public API that covers JMP's main DOE workflow, not a re-implementation of JMP (no data-table platform, scripting language, or regulated-industry validation). Every Studio feature must call public library functions only, and Studio work happens only in P2.5 or later consolidation weeks.
- **Reuse before build (Scientist decision 2026-11-19, "分析端可以直接调用它们或者和它们对接，不用自己重复造轮子").** TorchOED's analysis side implements only what is specific to designed experiments: structure-aware models and error terms (blocks, whole plots, REML wiring for split-plot), design-aware ANOVA and effect tables, prediction-profiler data, desirability, simulation-based power, bootstrap and batched fits for closed-loop rounds. General statistical machinery is reused, not rebuilt: CPU reference fits come from established libraries (e.g. statsmodels), GPU statistics packages are called through thin optional adapters, and GP surrogates and sequential optimisation are left to BoTorch/Ax. Adapters live behind optional extras (`pip install torchoed[...]`) and are never core runtime dependencies. Before any adapter is built, a Mentor landscape review checks each candidate package (existence, licence, maintenance, numerical validation against R, API stability) and records the choice; a package that fails the review is not used. Every analysis result is checked against R (`lm`, `lme4`/`nlme`) on published examples.
- **Backends and mobile groundwork (Scientist decision 2026-11-26: "同意加 P5/P6").** P5 and P6 start only after 1.0 and do not delay 1.0 or the technical report. Groundwork happens earlier at no extra scope: the P2.5 Studio is built responsive and installable as a PWA so P6 can package it, and P3 routes search-heavy work through one internal backend interface so P5 can plug in without changing the public API.
- **Publication (Scientist decision 2026-11-28: "先不投稿 JOSS…整理好技术报告就行…整理出完整项目了，再投不需要版面费的期刊或者会议").** No paper submission for now. Keep a living technical report instead (method, certificates, external-oracle evidence, held-out record, GPU measurements), published as an arXiv preprint at 1.0 and updated with later releases. Submit only after the project is complete, as the Scientist judges, and only to a venue with no publication fee. Candidates: Journal of Statistical Software, JMLR MLOSS, JOSS, SciPy Proceedings. The Scientist chooses the venue.
- **Post-1.0 order and detailed plan (Scientist decision 2026-11-28: "全加，P9 提前，同时把新的整体研发计划全面细化下").** After 1.0 the order is P5 → I → P9 → P7 → P6 → P8 → P10. Every new direction lives behind an optional extra or a separate package; the core runtime dependency stays torch only. Each phase starts with a Mentor landscape review and a reviewed gate. The detailed plan, with week blocks, oracles, exit criteria and decision points, is in [`docs/ROADMAP.md`](ROADMAP.md); this file wins if the two disagree.
- **No claim without evidence.** "Beats X" only on a frozen public benchmark; "nobody else does Y" only after a Mentor landscape review.
- **Held-out benchmark.** A case set the loop never optimizes against is run once per week and reported as-is.
- **Independent math review.** Every new gate document is attacked by a reviewer without the author's context (fresh subagent or the Mentor) before it is merged.
- **External oracles (R, Julia, PyDOE, …).** Dev-only references, never runtime dependencies. **R (and Julia) run on GitHub Actions** through the manually triggered workflow `.github/workflows/r-oracle.yml` (`workflow_dispatch` only, never on push or pull request, so ordinary CI never needs them); Colab is used only for GPU measurements (Scientist decision 2026-11-19, after repeated Colab allocation failures). Every run records exact interpreter and package versions (`sessionInfo()`, `Pkg.status()`) and the workflow run id; inputs are frozen as files in the repo, outputs are downloaded as the run's artifact and re-scored by one shared TorchOED metric, ≤ 10 evidence files. A reference that cannot be reproduced from the recorded versions is reported as NOT_RUN, not approximated.
- **Weekly cadence (Scientist decisions 2026-11-01 and 2026-11-14: auto-advance, immediate effect).** Weeks are numbered from 2026-10-31 (week 1) and advance when their goals are met. The loop drafts the next `docs/WEEK_GOAL.md` along the phases and the matrix, and it takes effect immediately; the Scientist may hold or redirect at any time (close the Issue, comment `SCIENTIST: ...`, or tell the Architect in chat, which the Architect relays with the time and the Scientist's words). Every 4th week (4, 8, 12, …) is a **consolidation week**: no new features — refactor, delete dead code, refresh docs and the matrix, test-suite speed, dependency upkeep, close stale Issues, release. Each new week adds fresh frozen cases to the held-out benchmark. This file changes only by the Scientist.
